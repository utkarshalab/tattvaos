# Tattva OS — Filesystem Layout

> The root namespace of a running Tattva OS system: what every top-level folder
> is for, who may touch it, how long its contents live, what may run from it, and
> which subsystem implements it.

**Status:** layout frozen. The eleven top-level folders below are final and will
not be renamed, added to, or removed. Sub-folder detail may still grow, within the
rules of §10. Implementation has not started; the subsystem map in §9 records
where every source folder lands and which source trees will own each part.

## 1. Principles

1. **Eleven folders, one job each.** Every top-level folder has exactly one
   storage class and one access rule. Nothing at the root is "misc".
2. **The folder decides the lifetime.** A write's durability is known from its
   path alone — `data/`, `user/` and `share/` persist, `tmp/` and `sys/run/`
   vanish on boot, `boot/` and `app/` never accept writes.
3. **Signed code, writable state.** All code comes from signed, read-only layers
   (`boot/`, `app/`). An update replaces a layer whole; nothing is patched in
   place.
4. **Capabilities, not permission bits.** There are no owner/group/other mode
   bits. Every access is a `usrauth_check(subject, object, class, verb)` decision
   (§4). The layout gives each subject a small default set of paths; anything
   beyond that must be granted.
5. **Admin is a user, not a mode.** The administrator lives at `user/admin/` like
   everyone else. Its extra authority comes from capabilities, and even admin
   cannot write `boot/` or `app/` except through a signed update.
6. **Only signed code runs.** Scripts may live anywhere, but native code and
   kernel-loaded programs run only from `app/` and `boot/mod/` (§5).
7. **Short, plain names.** Lower case, no spaces; top-level names are three to
   five letters. The same word means the same thing at every depth.
8. **Restore = signed layers + five folders.** Fresh signed layers plus a restore
   of `conf`, `sec`, `data`, `user` and `share` reproduce the whole system (§7.3).

## 2. The root at a glance

```
/
├── boot/    boot loaders, kernel image, boot config, signatures, drivers, previous image
├── sys/     live system state: tasks, memory, cpu, devices, network, AI, runtime
├── conf/    system configuration
├── sec/     identities, capabilities, keys, trust, secrets, firewall rules, policy
├── app/     applications, commands, shared libraries, base AI models
├── data/    persistent application data
├── user/    one home per user
├── share/   files shared between users and groups
├── keep/    what the system keeps about itself: logs, backups, dumps, updates, trash
├── tmp/     scratch space and temporary scripts
└── vol/     storage from outside the system
```

### Storage classes

| Class | Folders | Backing | Survives reboot | Written by |
|---|---|---|---|---|
| **Image** | `boot/`, `app/` (except `app/model/`) | signed read-only system image | yes | signed update only |
| **Model layer** | `app/model/` | signed read-only model layer | yes | signed model update only |
| **Virtual** | `sys/` (except `sys/run/`) | generated by the kernel on read | n/a | kernel |
| **Volatile** | `sys/run/`, `tmp/` | RAM | **no** — cleared at boot | system, apps, users |
| **Config** | `conf/` | disk | yes | admin |
| **Secure** | `sec/` | disk, encrypted, TPM-unsealed | yes | admin, via the auth service |
| **Persistent** | `data/`, `user/`, `share/` | disk | yes | apps, users |
| **Records** | `keep/` | disk (`keep/bak/` may be its own disk) | yes | system services; `trash/` by its owner |
| **External** | `vol/` | whatever is attached | depends on the device | as granted |

## 3. Folder reference

Each entry lists purpose, full contents, access and lifetime.
Access uses three subject kinds — **user** (a logged-in person), **app** (a
running application, identified by its signed manifest) and **admin** (the user
`admin`). "—" means no access.

### 3.1 `boot/` — the bootable image

The kernel and everything needed to start it. Read-only, signed, measured into
the TPM at boot.

```
boot/
├── loader/          second-stage and firmware boot loaders, panic-recovery stub
├── kernel.img       the kernel image
├── boot.conf        boot parameters: console, memory limits, root volume, flags
├── sig/             signatures over loader/, kernel.img, boot.conf, mod/ and the app/model layers
├── mod/             loadable drivers, signed together with the kernel
└── prev/            the previous image, kept for one-step rollback
```

| | user | app | admin |
|---|---|---|---|
| read | — | — | yes |
| write | — | — | signed update only |

- An update is staged in `keep/upd/`, verified, the running image moves to
  `prev/`, and the new one takes its place. A failed boot falls back to `prev/`.
- `sig/` must sit beside what it signs, so it lives here rather than in `sec/`.
- The first-stage loader occupies the disk's boot sector, before any filesystem
  exists, so it has no path. Everything it loads lives in `boot/`.

### 3.2 `sys/` — live system state

A synthetic tree. Nothing under `sys/` (apart from `sys/run/`) is stored; every
read is answered by the kernel at that moment. Reading a file inspects the
system; writing a control file changes it.

```
sys/
├── tasks/           one entry per running task: state, memory, cpu time, subject
├── mem              physical / virtual / free / per-NUMA-node figures
├── cpu              cores, features, frequency, load
├── uptime
├── version          kernel version and build id
├── log              system log ring (in RAM, fixed size)
├── users/           logged-in users and their live sessions
├── dev/             devices, created when hardware is discovered
│   ├── console  null  zero  rand  clock
│   ├── blk/         block devices: disk0, disk1, …
│   ├── input/       kbd0, mouse0, …
│   └── gpu/         gpu0, …
├── net/             network as files
│   ├── <iface>/     per interface: state, address, counters; write `up` / `down`
│   ├── conn/        live connections
│   ├── fw/          live firewall state: rule hits, drops, currently blocked sources
│   ├── dns
│   └── routes
├── ai/              AI runtime (§6)
│   ├── models/      loaded models: memory used, device, quantization
│   ├── accel/       accelerator use, linked to dev/gpu/
│   └── jobs/        active inference and training jobs: throughput, queue depth
└── run/             runtime state in RAM: sockets, locks, task ids, sessions
```

| | user | app | admin |
|---|---|---|---|
| read | own tasks, own session, own jobs | own tasks, own jobs | everything |
| write | — | — | control files |

- `sys/log` is the live ring. Anything that must outlive a reboot is drained to
  `keep/log/`.
- `sys/run/` is the only stored part of `sys/`; it is RAM-backed and empty at
  every boot.

### 3.3 `conf/` — system configuration

How the system is set up. Plain, human-readable records.

```
conf/
├── system           hostname, locale, timezone, default shell, boot targets
├── net              interfaces, addresses, dns servers, routes
├── time             clock source, time servers
├── ai               default model, accelerator limits, memory budget for models
└── apps/            admin policy per application: apps/<app>
```

| | user | app | admin |
|---|---|---|---|
| read | `system`, `time` | own `apps/<app>`, `ai` | everything |
| write | — | — | everything |

- Secrets never go in `conf/` — they go in `sec/`. That lets admin hand out
  config access without exposing a single key or hash.
- Admin may **lock** a key in `conf/apps/<app>`; a locked key cannot be
  overridden by a user (§7.1).

### 3.4 `sec/` — security

Everything that decides who may do what, and everything secret. Encrypted at
rest; unsealed at boot by the TPM against the measured boot state. No subject
reads these files directly — every access goes through the auth service.

```
sec/
├── users            identity records: name, id, credential hashes, integrity level
├── groups           groups and their members
├── caps/            capability grants: which subject may do which verb on which path
├── keys/            the system's own private keys and certificates
├── trust/           trusted public keys and CA certificates (system, apps, models, TLS)
├── vault/           application secrets: vault/<app>/ — tokens, API keys
├── fw/              firewall rules: allow / deny, rate limits, blocked sources
└── policy/          login rules (lockout, credential strength), sandbox defaults,
                     mandatory labels
```

| | user | app | admin |
|---|---|---|---|
| read | — (change own credential via the auth service) | own `vault/<app>/` | via the auth service |
| write | — | — | via the auth service |

- Every change is recorded in `keep/log/sec/`.
- `fw/` is read by the firewall through the auth service, like everything else
  here; only admin changes it.
- Grants carry an expiry by default; permanence is the explicit exception.
- Backups of `sec/` stay encrypted inside `keep/bak/`.

### 3.5 `app/` — applications, commands, libraries, models

Everything that is code or shipped content. Read-only; always signed. Only the
three reserved folders `lib/`, `cmd/`, `model/` and application folders may
appear here.

```
app/
├── lib/                 shared libraries
│   └── <lib>/           one folder per library: code + manifest (version, hash)
├── cmd/                 small commands, one executable each
│   └── <command>
├── model/               base AI models — separate signed layer (§6)
│   └── <model>/
│       ├── manifest     name, version, architecture, quantization, size, hash, signature
│       ├── weights/     weight files, possibly split into shards
│       ├── tokenizer/   vocabulary and merges
│       └── conf/        default generation settings: context length, temperature, …
└── <app>/               a full application
    ├── main             the executable
    ├── manifest         identity, version, signature, requested capabilities and models
    ├── conf/            default configuration
    ├── lib/             private libraries (optional)
    └── res/             assets: icons, fonts, data files, bundled scripts
```

| | user | app | admin |
|---|---|---|---|
| read | yes (`model/` only via an app) | yes (`model/` only those in its manifest) | yes |
| write | — | — | signed update only |

**Three kinds of code live here:**

| Kind | Where | Owns state? | Runs as |
|---|---|---|---|
| **Library** | `app/lib/<lib>/` | no | linked into whoever uses it |
| **Command** | `app/cmd/<command>` | no — works on the caller's files | the caller (user or app) |
| **Application** | `app/<app>/` | yes — `data/<app>/`, `tmp/app/<app>/`, its own log | itself, with the capabilities in its manifest |

- Commands are small single-purpose tools — file, directory, text, process,
  archive, system and developer utilities. They hold no authority of their own;
  anything a command does, the caller could do.
- Anything with its own configuration, state or long-lived process is an
  application, not a command: the shell, the editor, the dashboard.
- Applications are statically linked by default. `app/lib/` holds the libraries
  where one shared copy is worth it.
- The **manifest is the app's identity**: what the code is, not a secret it
  holds. Capabilities and models an app needs beyond its defaults (§4.2) must be
  listed there, and are granted at install time.

### 3.6 `data/` — application data

Persistent state owned by applications.

```
data/
└── <app>/           databases, state, indexes — layout chosen by the app
    ├── ai/          fine-tunes, adapters, checkpoints, vector indexes (if the app uses AI)
    └── cache/       rebuildable cache; safe to delete at any time
```

| | user | app | admin |
|---|---|---|---|
| read / write | — | own `data/<app>/` | everything |

- Removing an application removes `app/<app>/`, `data/<app>/` and
  `tmp/app/<app>/`. Nothing is left behind.
- `cache/` is excluded from backups.

### 3.7 `user/` — user homes

One folder per user. Owner-only.

```
user/
├── admin/                   the administrator's home
└── <name>/
    ├── conf/                personal settings per app: conf/<app>
    ├── app/                 per-user application data: app/<app>/ (incl. personal AI adapters and memory)
    └── files/               the user's own documents and kept scripts
```

| | owner | other user | app | admin |
|---|---|---|---|---|
| read / write | yes | — | the running user's `app/<app>/` and `conf/<app>` | read |

- A home can be encrypted with a key unlocked at login.
- Quotas apply per home.

### 3.8 `share/` — shared files

The one place where users meet. Without it, moving a file between two users
would need admin.

```
share/
├── all/             every user may read and write
└── <group>/         members of that group only, as listed in sec/groups
```

| | member | non-member | app | admin |
|---|---|---|---|---|
| read / write | yes | — | as granted | yes |

- Access comes entirely from groups already in `sec/groups`; no second
  permission system is introduced.

### 3.9 `keep/` — system records

What the system keeps *about itself*, as opposed to the content it holds.

```
keep/
├── log/             persisted logs
│   ├── sys/         kernel and service logs
│   ├── app/<app>/   per-application logs
│   └── sec/         security audit: logins, grants, denials, credential changes
├── bak/             backups — dated snapshots of conf, sec, data, user, share
├── dump/            crash dumps and panic reports
├── upd/             downloaded system images, packages and models, verified and waiting
└── trash/<name>/    deleted files, per user, kept until emptied
```

| Sub-folder | Written by | Read by | Backed up |
|---|---|---|---|
| `log/` | system; apps write only their own `log/app/<app>/` | admin | optional |
| `bak/` | backup service | admin | — (it is the backup) |
| `dump/` | kernel / panic handler | admin | no |
| `upd/` | update service | admin | no |
| `trash/<name>/` | owner | owner | no |

- `keep/bak/` should be mounted from a separate disk or a remote share, so a
  backup survives the failure of the disk it protects.
- `keep/log/sec/` is append-only and hash-chained.

### 3.10 `tmp/` — scratch space and temporary scripts

RAM-backed. Empty at every boot.

```
tmp/
├── app/<app>/           scratch for one application
│   └── script/          scripts the app generates and runs: jobs, hooks, pipelines
└── user/<name>/         private scratch for one user
    └── script/          one-off scripts the user writes or downloads
```

| | owner | others | admin |
|---|---|---|---|
| read / write | own folder | — | yes |

- Split by owner so applications and users never share a namespace, and no one
  can read or swap another's scripts.
- `tmp/` is the natural home for scripts that are meant to be thrown away. A
  script worth keeping belongs in `user/<name>/files/`; a script that ships with
  the system belongs in an app (`app/<app>/res/`) or becomes a command.
- How scripts run, and why that is safe from `tmp/`, is in §5.

### 3.11 `vol/` — outside storage

Storage that does not belong to the system image or its disks.

```
vol/
├── ext/             physical, attached: usb0, sd0, disk1, …
└── att/             remote or virtual: network shares, host folders, object stores, model stores
```

| | user | app | admin |
|---|---|---|---|
| read / write | as granted | as granted | yes |

- Volumes are mounted when they appear and named by kind and index.
- Foreign on-disk formats are read and written through the compatibility drivers
  (§9), so a volume formatted elsewhere still mounts here.

## 4. Access model

### 4.1 One decision function

Tattva OS runs in a single address space, so access is not enforced by
privilege rings. It is enforced by one reference monitor, `usrauth`:

```
usrauth_check(subject, object, class, verb) -> allow | deny
```

Every filesystem operation passes through it. Authority is the **intersection**
of every layer (mandatory labels, integrity level, held capability, token
caveats, expiry, policy) — no layer can grant what another denies.
See [`security/usrauth/README.md`](../security/usrauth/README.md).

### 4.2 Default grants

What each subject receives with no further configuration:

| Subject | Owns (read + write) | Reads |
|---|---|---|
| **user** `<name>` | `user/<name>/`, `tmp/user/<name>/`, `keep/trash/<name>/` | `app/` (not `app/model/`), `conf/system`, `conf/time`, `share/all/`, own entries in `sys/` |
| **app** `<app>` | `data/<app>/`, `tmp/app/<app>/`, `keep/log/app/<app>/` | `app/`, models listed in its manifest, `conf/apps/<app>`, `conf/ai`, `sec/vault/<app>/`, the running user's `user/<name>/app/<app>/` and `conf/<app>` |
| **command** | nothing of its own | whatever its caller can reach |
| **admin** | everything except `boot/`, `app/` | everything |

Group membership adds `share/<group>/`. Any other path needs an explicit grant
in `sec/caps/` (for users and groups) or a request in the app's `manifest`.

### 4.3 Access matrix

| | `boot` | `sys` | `conf` | `sec` | `app` | `app/model` | `data` | `user/self` | `user/other` | `share` | `keep` | `tmp/self` | `vol` |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| **user** | — | own | part (read) | via service | read | — | — | full | — | groups | own trash | full | granted |
| **app** | — | own | own (read) | own vault | read | manifest | own | own app data | — | granted | own log | full | granted |
| **admin** | update | full | full | via service | read | read | full | full | read | full | full | full | full |

## 5. What may run

Everything in Tattva OS shares one address space at one privilege level. Loaded
native code is therefore trusted completely — so *which* code may load is the
most important rule in the layout.

| Kind | May run from | Authority |
|---|---|---|
| **Native code** (applications, commands, libraries, drivers) | `app/` and `boot/mod/` only — signed layers | the app's manifest; commands and libraries inherit the caller's |
| **Kernel-loaded programs** (packet and trace programs) | `app/lib/` only — signed, then verified before loading | the app that attaches them |
| **Scripts** (run by the shell, `ish`) | anywhere the caller can read — including `tmp/`, `user/`, `share/`, `vol/` | exactly the subject that started it, never more |
| **Model weights** | `app/model/` (base), `data/<app>/ai/` and `user/<name>/app/<app>/` (adapters) | data, not code — read by the inference engine for an app that holds the grant |

- **Native code never loads from `tmp/`, `data/`, `user/`, `share/` or `vol/`.**
  There is no "run this binary I downloaded": new native code arrives as a signed
  package, lands in `keep/upd/`, is verified against `sec/trust/`, and installs
  into `app/`.
- **Scripts are safe in `tmp/` because they carry no authority.** A script can
  only do what the person or app running it could already do by hand. Dropping a
  script into someone's `tmp/` is impossible (§3.10), and running one never
  raises privilege.
- Scripts run by an application use the application's grants; scripts run by a
  user use the user's.

## 6. AI models

Tattva OS ships its own models and runs inference and training natively. Each
kind of AI artefact sits in the folder whose lifetime and access already fit it —
there is no separate AI root.

| What | Where | Why |
|---|---|---|
| **Base models** — shipped, signed | `app/model/<model>/` | read-only, signed, shared by every app that is granted them |
| **Fine-tunes, adapters, checkpoints** | `data/<app>/ai/` | produced on this machine, owned by the app that trained them |
| **Embeddings, vector indexes** | `data/<app>/ai/` (rebuildable parts in `data/<app>/cache/`) | persistent app state |
| **Personal adapters, per-user memory** | `user/<name>/app/<app>/` | private to that user |
| **Loaded models, accelerator use, running jobs** | `sys/ai/` | live state, generated on read |
| **Inference and training scratch** | `tmp/app/<app>/` | RAM, gone at reboot |
| **Downloaded models awaiting install** | `keep/upd/` | verified like any other update |
| **Remote model stores** | `vol/att/` | outside storage |
| **AI defaults** — default model, memory budget, accelerator limits | `conf/ai` | admin policy |

- **The model layer is separate from the system image.** Models are large and
  change more often than the kernel, so `app/model/` is its own signed read-only
  layer: a model update never rebuilds the system image, and a system update never
  re-downloads models.
- **Models are granted, not ambient.** An app names the models it uses in its
  manifest; `usrauth` grants read access to those and no others. Users reach
  models only through an app.
- **Weights are mapped, not copied.** The inference engine maps weight files
  straight from storage into memory.
- **Backups** cover everything created on the machine (`data/`, `user/`). Base
  models are not backed up — the signed layer can always be fetched again.

## 7. Behaviour

How long each write lives is set by its storage class (§2).

### 7.1 Configuration lookup

When an application reads a setting, the first match wins:

```
user/<name>/conf/<app>   →   conf/apps/<app>   →   app/<app>/conf/
   user preference              admin policy           app default
```

A key that admin marks **locked** in `conf/apps/<app>` skips the user layer.
Model settings follow the same order, ending at `app/model/<model>/conf/`.

### 7.2 Boot order

1. The first-stage loader starts `boot/loader/`, which verifies
   `boot/kernel.img` and `boot/mod/` against `boot/sig/` and measures each into
   the TPM.
2. The kernel mounts the signed system image read-only at `boot/` and `app/`,
   then the signed model layer at `app/model/`.
3. `sys/` is generated; `sys/run/` and `tmp/` are created empty in RAM.
4. The TPM unseals the volume key; `sec/` is decrypted and the auth service
   starts.
5. `conf/`, `data/`, `user/`, `share/` and `keep/` are mounted read-write.
6. Devices present at boot appear under `sys/dev/`; attached storage under
   `vol/`.
7. Applications start, each confined to its default grants (§4.2).

### 7.3 Backup and restore

| Folder | Backed up | Reason |
|---|---|---|
| `conf/`, `sec/`, `data/`, `user/`, `share/` | **yes** | cannot be rebuilt |
| `boot/`, `app/` (incl. `app/model/`) | no | come from signed layers; `boot/prev/` covers rollback |
| `sys/`, `tmp/` | no | live or temporary |
| `data/*/cache/` | no | rebuildable |
| `keep/` | no (logs optional) | it holds the backups |
| `vol/` | no | someone else's storage |

Restore: boot fresh signed layers, then restore the five backed-up folders from
the chosen snapshot in `keep/bak/`.

### 7.4 Updates

1. Download into `keep/upd/` — a system image, a package, or a model.
2. Verify the signature against `sec/trust/`.
3. System image: move the running image to `boot/prev/`, install the new one,
   reboot; if it fails to come up, boot from `boot/prev/`.
   Package or model: install into `app/` or `app/model/` as a new signed layer
   and swap atomically.

### 7.5 Deleting

User-initiated deletes in `user/` and `share/` move the file to
`keep/trash/<name>/`. Emptying trash is the only true delete. Deletes made by
applications inside their own `data/<app>/` are immediate.

| I have… | It goes in |
|---|---|
| a new application | `app/<app>/` (installed as a signed package) |

| a cache that can be rebuilt | `data/<app>/cache/` |

| a user's own setting | `user/<name>/conf/<app>` |

| a user's login key | `user/<name>/conf/ssh` |
| a firewall rule | `sec/fw/` |
| a personal document or a script worth keeping | `user/<name>/files/` |
| a file for a team | `share/<group>/` |

| scratch data | `tmp/user/<name>/` or `tmp/app/<app>/` |

| a network share or remote store | `vol/att/` |

## 9. Subsystem map

Which source trees implement each part of the layout. No code has been changed
for this document; the map records ownership for when implementation begins.

### 9.1 Every source folder

Where each top-level folder of the source tree ends up on a running system.
There are two builds of the system image, both using this same layout:

- **Release image:** what ships. Contains groups A and B below.
- **Development image:** release plus the on-target test and benchmark runners
  from group C.

#### A. Built into the kernel image (`boot/`)

| Source | Lands in | Notes |
|---|---|---|
| [`boot/stage1/`](../boot/stage1/) | the disk's boot sector | has no path (§3.1) |
| [`boot/stage2/`](../boot/stage2/), [`boot/uefi/`](../boot/uefi/) | `boot/loader/` | loads and verifies `boot/kernel.img` |

## 10. Naming rules and reserved names

- Lower case only, no spaces. Top-level names are three to five letters; deeper
  names stay short and plain.
- `<app>` is the application's name from its manifest; `<name>` is the user's
  name from `sec/users`; `<group>` is from `sec/groups`; `<model>` is from the
  model's manifest.
- The same word means the same thing at every depth: `conf/` is configuration in
  `/conf`, `app/<app>/conf/`, `app/model/<model>/conf/` and `user/<name>/conf/`;
  `app/` is application material in `/app`, `user/<name>/app/` and `tmp/app/`;
  `ai/` is AI material in `sys/ai/` and `data/<app>/ai/`.
- Configuration files are named `*.conf` (e.g. `boot/boot.conf`).

**Reserved names** — no application, user or group may take these:

| Where | Reserved |
|---|---|
| `app/` | `lib`, `cmd`, `model` |
| `tmp/` | `app`, `user` |
| `user/` | `admin` |
| `share/` | `all` |

**Growing the layout.** A new sub-folder may be added under an existing top-level
folder only when it shares that folder's storage class and access rule. The eleven
top-level folders are fixed.
